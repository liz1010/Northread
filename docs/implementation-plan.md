# 第一部分 · 第一阶段

## 1. 这一版要验证什么

Northread 的第一阶段不是做一个完整的商业产品，而是做出一个创建者本人愿意每天使用的
私人阅读决策系统。

只验证一个假设：

> 当系统理解我的真实目标、信任来源和可用时间时，它能否每天从大量候选内容中，
> 选出不超过三项真正值得投入时间的内容，并通过反馈持续提高选择质量？

这一阶段不以注册用户数、停留时间或功能数量为成功标准。

判断"是否该往下做"的依据只有第 3 节的成功标准和第 7 节的评估结果。功能数量、
接入了多少平台、代码写得多漂亮，都不是依据。

## 2. 第一版使用场景

每天打开 Northread 后，用户看到：

1. 今天最值得读的一项
2. 有时间再读的两项
3. 每项内容对应的目标、推荐原因、预计耗时和推荐置信度
4. 今天被过滤的内容数量及主要过滤原因
5. 昨天阅读后留下的知识、反馈或行动

用户完成阅读后，可以快速反馈"为什么有用或没用"。系统利用反馈改善下一次推荐，
但任何 AI 学习到的信源调整都必须可见、可撤销。

界面参考 [今日首页概念图](assets/northread-today-concept.svg)。

## 3. 成功标准

个人可用版连续试用 14 天，并满足大部分以下条件：

- 至少 10 天主动打开 Northread
- 至少 8 天阅读或认真查看了一项推荐
- 每天决定"读什么"的时间控制在 5 分钟以内
- 至少 60% 的第一推荐被标记为"值得现在读"
- 至少产生 5 条可保留的知识笔记
- 至少产生 3 个实际行动、实验或决策
- 能明确指出系统如何根据反馈改善了推荐
- 使用者愿意停止查看原始 RSS 收件箱，把 Northread 作为主要入口

如果没有达到标准，应优先修正推荐质量和交互闭环，而不是增加更多信息源。

## 4. 范围

### 4.1 必须实现

- 单用户使用，不做注册和多租户
- 创建、编辑和暂停目标
- 为目标记录背景、当前水平、期望产出和每周可用时间
- 添加 RSS/Atom 信源
- 手动提交网页链接
- 设置来源的全局权重、目标权重和推荐频率
- 定时获取新内容并提取正文
- 内容去重、初筛、目标匹配和最终重排
- 每日最多三项推荐
- 展示具体推荐理由、预计耗时、置信度和评分依据
- 支持有意义的显式反馈
- 保存阅读状态、笔记和行动项
- 提供最小每周复盘
- 记录每次模型调用、prompt 版本和评分结果，便于调试
- 一条不依赖界面的命令行路径，能对基线集重跑整条推荐管线（见第 7 节）

关于语言：**界面以中文为主，内容中英文都要支持**。这意味着：

- 全部界面文案、模型输出（推荐理由、置信度说明、每周复盘）统一用中文
- 候选内容既有中文信源，也有英文文章和论文，二者进同一条管线、同一套评分
- 遇到英文材料时，标题保留原文，推荐理由和摘要用中文
- 不做全文翻译。翻译会让人误以为读过了，与"AI 不替你阅读"冲突

### 4.2 第一阶段明确不做

- 微信读书自动同步
- Twitter/X、YouTube 或播客账号级自动同步
- 浏览器插件和原生移动 App
- 多用户、团队空间和社交功能
- 自动生成完整知识图谱
- 复杂间隔重复系统
- 付费、订阅和商业化能力
- 完全自主地修改用户权重

不做不代表不重要，而是避免平台接入和功能广度延迟核心推荐闭环。YouTube、书籍和
其他内容可以先通过手动链接或手动记录进入系统。这些方向见第二部分。

## 5. 产品页面

五个页面，不多不少。界面参考
[三栏阅读工作台概念图](assets/northread-workspace-concept.svg)。

### 5.1 今日（Today）

整个产品的核心页面，只呈现：

- 第一推荐
- 两项候选推荐
- 推荐理由和对应目标
- 预计阅读时间和推荐置信度
- 阅读、稍后、忽略和反馈操作
- 今日过滤统计

今日页不显示无限滚动，也不展示"999+ 未读"。主动隐藏噪声本身就是产品价值，
所以过滤数量要显示，被过滤的内容默认不显示。

### 5.2 目标（Goals）

- 当前目标及状态
- 目标描述、时间范围和期望产出
- 当前知识背景
- 每周时间预算
- 目标使用的信源策略
- 简单的进展与近期行动

第一版不要求 AI 自动生成完整知识地图，只维护可编辑的"已知主题"和"待补知识"。

### 5.3 信源（Sources）

- RSS 地址、名称和抓取状态
- 来源的全局与目标权重
- 每周最大推荐次数
- 重要、普通、探索、降低权重和静音状态
- 最近为什么提高或降低了该来源的优先级

### 5.4 资料库（Library）

- 已推荐、已读、保存和忽略的内容
- 搜索与简单筛选
- 用户笔记和行动项
- 每条内容当时的推荐理由和反馈

### 5.5 复盘（Review）

- 本周哪些推荐真正有帮助
- 哪些来源产生了最多有效内容
- 哪些内容重复、太浅或不合时机
- 新增知识、判断变化和行动
- AI 建议的信源调整，由用户确认后生效

## 6. 推荐管线

第一版不让强模型读取所有文章，而是采用分层管线。

```text
RSS 与手动链接
        ↓
正文提取和标准化
        ↓
URL、标题与语义去重
        ↓
语言、时间、静音规则和来源频率过滤
        ↓
低成本模型进行目标相关性初筛
        ↓
保留高潜力候选内容
        ↓
强模型结合目标、知识缺口和历史反馈进行比较重排
        ↓
名额分配，生成每日三项及可解释推荐理由
        ↓
用户反馈与阅读结果
        ↓
更新统计，并提出可撤销的权重调整建议
```

### 6.1 初筛

初筛输入尽量只包含标题、来源、发布时间、摘要和少量正文，以控制延迟和成本。
初筛判断：

- 是否与任一活跃目标相关
- 是否明显重复
- 是否低信息量或标题党
- 是否值得进入最终候选集

### 6.2 最终重排

最终重排应进行候选内容之间的相对比较，而不只是分别生成孤立分数：

> 如果今天只能选择一项，哪一项最能推动目标？它相对于其他候选新增了什么？

最终结果至少包含：

- 对应目标
- 推荐级别
- 推荐原因
- 预期获得的知识或方法
- 预计阅读时间
- 是否建议完整阅读、速览或只读指定部分
- 最关键的加权因素
- 置信度和可能的不足

界面上不出现没有解释的裸分数。展示分数时必须同时能展开它的构成
（目标相关性、信源权重、知识缺口、新颖度，减去重复度和阅读成本）。

### 6.3 冷启动与名额分配

第一天没有任何反馈数据，也没有来源表现统计。这时必须避免用零数据的先验制造假精度：

1. 信源权重只取用户手动设置的初始值，AI 不提任何调整建议
2. 评分公式中的"信源策略权重"项取中性值 1.0
3. 目标相关性完全由模型判断，不掺入历史表现项
4. 某个来源累计出现至少 5 次、且至少有 3 次显式反馈之后，才开始参与权重建议

多个目标同时活跃时，每日三条名额这样分：

- 不按目标平均分。先按各目标"本周时间预算剩余比例"排序，前两个目标各占一条
- 第三条给全局最高分，可以来自任一活跃目标
- 某个目标连续 5 天没拿到名额，第 6 天强制给它一条，避免长期饿死
- 暂停状态的目标不参与分配

抑制单一来源垄断：

- 同一来源每天最多进入一条推荐，每周最多三条
- 同一作者每周最多两条
- 用户可以为特定来源单独放宽，但放宽是显式操作，不能由 AI 自动完成

### 6.4 权重调整

第一版采用"AI 建议、用户确认"的方式：

1. 用户提交显式反馈
2. 系统累计来源和内容类型的表现
3. AI 提出调整理由和建议幅度
4. 用户接受、修改或拒绝
5. 系统保存变更历史并支持撤销

在积累足够使用数据之前，不做完全自动的隐式权重学习。

## 7. 推荐质量的评估办法

这一节决定了整个第一阶段能不能收敛。没有它，改 prompt 只能凭感觉，
第 10 节阶段 3 的完成标准也无法判定。

### 7.1 标注集

阶段 0 标注的内容存为 `eval/baseline.jsonl`，每条包含：

- 内容元数据：标题、来源、发布时间、URL、正文摘要
- 关联的目标 ID
- 人工标签：`must_read` / `worth_reading` / `ignore`
- 一句话理由

标注顺序很重要：**先标完，再跑模型**。看过模型输出之后再标，标注就没有价值了。

初始规模 50 条，之后每两周补 10 到 20 条新标注，避免 prompt 过拟合到最初那批。

### 7.2 指标

只用三个，不要更多：

| 指标 | 定义 | 作用 |
|---|---|---|
| **precision@3** | 模型选出的三条里，人工标为 `must_read` 或 `worth_reading` 的比例 | 主指标 |
| **must_read 召回** | 人工标为 `must_read` 的内容，有多大比例进了当天三条 | 防止漏掉真正重要的 |
| **理由可验证率** | 推荐理由是否指向了具体目标、知识缺口或已读内容，而不是套话 | 只能人工看，不能自动算 |

第三个指标必须人工逐条判断。推荐解释流于套话是这类产品最容易出现的失败方式，
而它恰好是自动指标看不出来的。

### 7.3 评估命令

```bash
npm run eval -- --set eval/baseline.jsonl --prompt-version v3
```

输出写入 `eval/runs/<prompt-version>.json`，包含三个指标的汇总，以及每条内容的
模型分数、推荐理由和与人工标签的差异。

这条命令不依赖界面，所以阶段 3 就能反复跑，不用等阶段 4 的页面做完。

### 7.4 改 prompt 的规矩

- 任何 prompt 改动都要先在基线集上跑一次，并与上一版对比
- precision@3 下降就回滚，除非能说清楚这次下降为什么可以接受
- prompt 版本号写进 `model_runs`，线上出问题时能对上是哪一版
- 一次只改一处。同时改两处，指标动了也不知道是哪一处起的作用

## 8. 技术方案

为了让个人项目快速迭代，第一版采用单体架构。

### 8.1 应用

- **语言**：TypeScript
- **Web 框架**：Next.js
- **UI**：Tailwind CSS 与轻量组件库
- **数据库**：SQLite
- **数据访问**：Drizzle ORM
- **定时任务**：Node.js 脚本配合系统 cron，后续再替换任务队列
- **部署**：Docker Compose，本地或获准使用的内部环境

选择单一语言和单体架构，是为了减少个人开发期间的部署、调试和接口成本。

### 8.2 内容处理

- RSS/Atom 解析器
- Mozilla Readability 风格的网页正文提取
- 规范化 URL 和内容指纹去重
- 保存原始链接、提取文本和必要元数据
- 不默认永久保存受版权保护的完整第三方内容

语义去重需要 embedding。如果第一阶段拿不到可用的 embedding 接口，先只做 URL
规范化和标题指纹去重，把语义去重记为已知缺口，不要因为它阻塞整条链路。

### 8.3 模型适配

实现统一的模型接口：

```text
ModelProvider
├── scoreCandidates()
├── rerankCandidates()
├── explainRecommendation()
└── generateWeeklyReview()
```

优先支持 OpenAI-compatible API，以便在获准的前提下连接公司模型，同时保留未来切换
其他云端或本地模型的能力。模型地址、密钥和模型名只通过环境变量配置。

同时实现一个不调用任何模型的 `MockProvider`，用固定规则打分。它有两个用处：
在没有模型授权时也能跑通整条链路，以及在模型接口出问题时快速判断问题出在哪一层。

### 8.4 可观测性

每次模型调用保存：

- 时间与模型名称
- prompt 模板版本
- 输入内容 ID，不在普通日志中重复打印敏感正文
- 结构化输出
- 延迟与 token 用量
- 用户后来给出的反馈

这使推荐问题可以被复现，而不是只能凭感觉修改 prompt。

## 9. 最小数据模型

- `goals`：目标、背景、产出、时间预算和状态
- `knowledge_gaps`：目标下已知主题与待补知识
- `sources`：来源、类型、抓取配置和全局策略
- `goal_source_policies`：来源在特定目标下的权重和频率
- `items`：文章或手动内容的元数据、正文和去重指纹
- `item_goal_scores`：初筛与重排的分数、理由和模型版本
- `daily_recommendations`：每日候选、顺序及生成时上下文
- `feedback`：显式评价及原因
- `notes`：用户自己的知识笔记
- `actions`：阅读产生的行动与完成状态
- `model_runs`：模型调用记录、延迟和版本
- `policy_changes`：权重变更、原因及撤销信息

## 10. 实施阶段

### 阶段 0：建立真实测试基线

任务：

- 写下 1–3 个本人正在推进的目标
- 导出当前 RSS 订阅
- 选择 10–30 个真实信源
- 按第 7.1 节的格式标注约 50 篇历史内容
- 确认公司模型的授权范围、接口方式和数据使用边界

完成标准：

- `eval/baseline.jsonl` 存在，且标注是在没有看过模型输出的情况下完成的
- 至少有一个明确目标包含当前水平、期望产出和时间预算

### 阶段 1：应用骨架与数据

任务：

- 初始化 Next.js、SQLite 和 Drizzle
- 建立核心数据表和迁移
- 完成目标、信源两个页面的基础增删改查
- 添加环境变量模板和 Docker Compose
- 建立 `ModelProvider` 接口及 `MockProvider`

完成标准：

- 可以在浏览器中创建目标和 RSS 来源
- 重启应用后数据仍然存在
- 不连接真实模型也能跑通模拟流程

### 阶段 2：内容摄取

任务：

- 抓取 RSS/Atom
- 支持手动添加 URL
- 提取正文和阅读时间
- 完成 URL、标题和内容指纹去重
- 显示抓取失败及原因

完成标准：

- 真实信源可以稳定进入数据库
- 重复抓取不会产生重复内容
- 单个来源失败不会阻塞其他来源

### 阶段 3：推荐纵向闭环

任务：

- 接入公司允许使用的模型
- 实现结构化初筛输出
- 实现候选比较与最终重排
- 实现 6.3 节的冷启动规则和名额分配
- 实现 `npm run eval` 命令
- 保存评分、prompt 版本和推荐理由

完成标准：

- 对基线集跑出第一组 precision@3、must_read 召回和理由可验证率，作为后续对比的基准
- 推荐理由能指出具体目标和知识缺口，而不是通用套话
- 相同输入与配置下结果可复现

### 阶段 4：今日页与反馈

任务：

- 完成今日页面
- 增加阅读、保存、忽略和反馈操作
- 增加来源策略控制
- 统计来源和内容类型的有效率
- 生成权重调整建议并支持确认、拒绝和撤销

完成标准：

- 日常选择不需要查看原始 RSS 列表
- 一次反馈可以影响后续推荐或形成明确的策略建议
- 用户能解释为什么某个来源最近出现得更多或更少

### 阶段 5：阅读结果与复盘

任务：

- 增加自由笔记和结构化反思
- 从阅读中创建行动项
- 实现最小资料库
- 生成每周复盘

完成标准：

- 可以追踪一次推荐最终产生了什么知识或行动
- 周报能指出有效来源、主要噪声和下周调整建议

### 阶段 6：连续 14 天 Dogfood

任务：

- 每天真实使用，不同时查看另一个 RSS 收件箱
- 记录推荐失败案例，并把典型失败补进基线标注集
- 每周只修复最影响使用的前三个问题
- 比较第 1 周和第 2 周的 precision@3

完成标准：

- 按第 3 节成功标准作出继续、调整或停止判断
- 形成下一阶段需求清单，而不是凭想象增加功能

## 11. 立即开始的第一批任务

1. 写下第一个真实目标
2. 准备 10–30 个 RSS 信源
3. 按 7.1 节格式标注 50 篇内容
4. 初始化应用骨架和数据库
5. 完成目标与信源页面
6. 跑通第一个 RSS 到数据库的摄取流程

第一条可用路径应当是：

```text
创建目标
→ 添加一个 RSS
→ 抓取文章
→ 模型排序
→ 今日页展示一项推荐
→ 提交一次反馈
```

在这条路径跑通之前，不增加其他平台或复杂功能。

## 12. 第一阶段的安全与边界

- 只使用获准的公司模型、接口和凭证
- 在传输个人内容或外部全文前确认内部数据政策
- 密钥不进入 Git、数据库或普通日志
- 允许删除原文、模型记录和个人反馈
- 保留模型供应商替换能力

# 第二部分 · 第一阶段之后

以下内容在第一阶段**不实现、不设计、不预留接口**。列出来只是为了记住它们存在，
以及记住为什么现在不做。真正做哪一项，由连续使用数据决定，不预先承诺顺序。

## 13. Dogfood 之后的优先顺序

只有核心闭环通过验证后，按真实痛点选择下一项：

1. YouTube 手动链接的字幕与时间戳
2. 浏览器扩展或系统分享入口
3. 书籍、章节计划和笔记导入
4. 微信读书可行的授权或数据导入方式
5. Twitter/X、播客和其他平台的自动同步
6. 更完整的知识地图和延迟复习
7. 邀请少量同事独立使用

## 14. 待验证的平台接入

这些都要先验证平台提供的官方接口、数据导出能力和使用条款，再谈实现。
如果无法可靠且合规地同步，优先支持用户主动导入，不要依赖脆弱的自动化方式。

### 微信读书等阅读平台

需要同步的是书架、阅读进度、划线和笔记。连接必须基于用户明确授权，
且允许随时查看、断开连接和删除已同步的数据。

书籍和资讯的时间尺度不同，不能把一本书当作一条更长的 Feed 内容。需要：

- 判断一本书与当前目标的关系，以及是否值得完整阅读
- 根据目标推荐全书、重点章节或仅供查阅的部分
- 将目录映射到知识地图
- 根据可投入时间制定阅读计划并跟踪进度
- 汇总划线、批注和读后思考
- 将书中观点与文章、论文交叉关联

### YouTube 与播客

视频和音频是发现知识的入口，不是需要复制的信息流：

- 优先基于标题、描述、章节、字幕或转录判断价值，保留时间戳引用
- 长视频先帮助定位与目标最相关的片段，再由用户决定是否完整观看

### Twitter/X

- 优先识别可信作者、原创线程和高价值外链
- 对二手转述尽可能追溯原始文章、论文、数据或完整访谈
- 将短内容组合为围绕某个问题的主题脉络，而不是制造无限滚动
- 对缺少上下文、无法验证或主要依赖情绪传播的内容降低推荐权重

## 15. 更长期的产品能力

- 完整的目标—知识—阅读图谱，而不是可编辑的知识缺口列表
- 作者、媒体、论文和博客之间的信源关系网络，包括原始来源与转述、引用关系
- 间隔重复与延迟复习，验证知识保留率
- 完全自动的隐式权重学习，取代当前"AI 建议、用户确认"的模式
- 多用户、团队空间
- 付费与商业化

## 16. 对外开放前需要重新审查的事项

如果未来提供给公司外部用户使用，以下每一项都要重新审查，不能沿用第一阶段的结论：

- 模型许可与数据政策
- 第三方内容的版权与使用条款
- 个人数据的存储位置、保留期限和删除机制
- 第三方平台接入的授权范围与合规边界
