# Northread 个人可用版实施计划

## 1. 计划目标

Northread 的第一阶段不是做一个完整的商业产品，而是做出一个创建者本人愿意每天使用的
私人阅读决策系统。

第一阶段只验证一个核心假设：

> 当系统理解我的真实目标、信任来源和可用时间时，它能否每天从大量候选内容中，
> 选出不超过三项真正值得投入时间的内容，并通过反馈持续提高选择质量？

这一阶段不以注册用户数、停留时间或功能数量为成功标准。

## 2. 第一版使用场景

每天打开 Northread 后，用户看到：

1. 今天最值得读的一项
2. 有时间再读的两项
3. 每项内容对应的目标、推荐原因、预计耗时和推荐置信度
4. 今天被过滤的内容数量及主要过滤原因
5. 昨天阅读后留下的知识、反馈或行动

用户完成阅读后，可以快速反馈“为什么有用或没用”。系统利用反馈改善下一次推荐，
但任何 AI 学习到的信源调整都必须可见、可撤销。

## 3. 成功标准

个人可用版连续试用 14 天，并满足大部分以下条件：

- 至少 10 天主动打开 Northread
- 至少 8 天阅读或认真查看了一项推荐
- 每天决定“读什么”的时间控制在 5 分钟以内
- 至少 60% 的第一推荐被标记为“值得现在读”
- 至少产生 5 条可保留的知识笔记
- 至少产生 3 个实际行动、实验或决策
- 能明确指出系统如何根据反馈改善了推荐
- 使用者愿意停止查看原始 RSS 收件箱，把 Northread 作为主要入口

如果没有达到标准，应优先修正推荐质量和交互闭环，而不是增加更多信息源。

## 4. MVP 范围

### 4.1 必须实现

- 单用户使用，不做注册和多租户
- 创建、编辑和暂停目标
- 为目标记录背景、当前水平、期望产出和每周可用时间
- 添加 RSS/Atom 信源
- 手动提交网页链接
- 设置来源的全局权重、目标权重和推荐频率
- 定时获取新内容并提取正文
- 内容去重、初筛、目标匹配和最终重排
- 每日最多三项推荐
- 展示具体推荐理由、预计耗时和评分依据
- 支持有意义的显式反馈
- 保存阅读状态、笔记和行动项
- 提供最小每周复盘
- 记录每次模型调用、prompt 版本和评分结果，便于调试

### 4.2 暂不实现

- 微信读书自动同步
- Twitter/X、YouTube 或播客账号级自动同步
- 浏览器插件和原生移动 App
- 多用户、团队空间和社交功能
- 自动生成完整知识图谱
- 复杂间隔重复系统
- 付费、订阅和商业化能力
- 完全自主地修改用户权重

暂不实现不代表不重要，而是避免平台接入和功能广度延迟核心推荐闭环。
YouTube、书籍和其他内容可以先通过手动链接或手动记录进入系统。

## 5. 产品页面

### 5.1 Today

整个产品的核心页面，只呈现：

- 第一推荐
- 两项候选推荐
- 推荐理由和对应目标
- 预计阅读时间
- 阅读、稍后、忽略和反馈操作
- 今日过滤统计

Today 不显示无限滚动，也不展示“999+ 未读”。

### 5.2 Goals

- 当前目标及状态
- 目标描述、时间范围和期望产出
- 当前知识背景
- 每周时间预算
- 目标使用的信源策略
- 简单的进展与近期行动

第一版不要求 AI 自动生成完整知识地图，只维护可编辑的“已知主题”和“待补知识”。

### 5.3 Sources

- RSS 地址、名称和抓取状态
- 来源的全局与目标权重
- 每周最大推荐次数
- 重要、普通、探索、降低权重和静音状态
- 最近为什么提高或降低了该来源的优先级

### 5.4 Library

- 已推荐、已读、保存和忽略的内容
- 搜索与简单筛选
- 用户笔记和行动项
- 每条内容当时的推荐理由和反馈

### 5.5 Review

- 本周哪些推荐真正有帮助
- 哪些来源产生了最多有效内容
- 哪些内容重复、太浅或不合时机
- 新增知识、判断变化和行动
- AI 建议的信源调整，由用户确认后生效

## 6. 推荐管线

第一版不让强模型读取所有文章，而是采用分层管线。

```text
RSS 与手动链接
        ↓
正文提取和标准化
        ↓
URL、标题与语义去重
        ↓
语言、时间、静音规则和来源频率过滤
        ↓
低成本模型进行目标相关性初筛
        ↓
保留高潜力候选内容
        ↓
强模型结合目标、知识缺口和历史反馈进行比较重排
        ↓
生成每日三项及可解释推荐理由
        ↓
用户反馈与阅读结果
        ↓
更新统计，并提出可撤销的权重调整建议
```

### 6.1 初筛

初筛输入尽量只包含标题、来源、发布时间、摘要和少量正文，以控制延迟和成本。
初筛判断：

- 是否与任一活跃目标相关
- 是否明显重复
- 是否低信息量或标题党
- 是否值得进入最终候选集

### 6.2 最终重排

最终重排应进行候选内容之间的相对比较，而不只是分别生成孤立分数：

> 如果今天只能选择一项，哪一项最能推动目标？它相对于其他候选新增了什么？

最终结果至少包含：

- 对应目标
- 推荐级别
- 推荐原因
- 预期获得的知识或方法
- 预计阅读时间
- 是否建议完整阅读、速览或只读指定部分
- 最关键的加权因素
- 置信度和可能的不足

### 6.3 权重调整

第一版采用“AI 建议、用户确认”的方式：

1. 用户提交显式反馈
2. 系统累计来源和内容类型的表现
3. AI 提出调整理由和建议幅度
4. 用户接受、修改或拒绝
5. 系统保存变更历史并支持撤销

在积累足够使用数据之前，不做完全自动的隐式权重学习。

## 7. 建议技术方案

为了让个人项目快速迭代，第一版采用单体架构。

### 7.1 应用

- **语言**：TypeScript
- **Web 框架**：Next.js
- **UI**：Tailwind CSS 与轻量组件库
- **数据库**：SQLite
- **数据访问**：Drizzle ORM
- **定时任务**：Node.js 脚本配合系统 cron，后续再替换任务队列
- **部署**：Docker Compose，本地或获准使用的内部环境

选择单一语言和单体架构，是为了减少个人开发期间的部署、调试和接口成本。

### 7.2 内容处理

- RSS/Atom 解析器
- Mozilla Readability 风格的网页正文提取
- 规范化 URL 和内容指纹去重
- 保存原始链接、提取文本和必要元数据
- 不默认永久保存受版权保护的完整第三方内容

### 7.3 模型适配

实现统一的模型接口：

```text
ModelProvider
├── scoreCandidates()
├── rerankCandidates()
├── explainRecommendation()
└── generateWeeklyReview()
```

优先支持 OpenAI-compatible API，以便在获准的前提下连接公司模型，同时保留未来切换
其他云端或本地模型的能力。模型地址、密钥和模型名只通过环境变量配置。

### 7.4 可观测性

每次模型调用保存：

- 时间与模型名称
- prompt 模板版本
- 输入内容 ID，不在普通日志中重复打印敏感正文
- 结构化输出
- 延迟与 token 用量
- 用户后来给出的反馈

这使推荐问题可以被复现，而不是只能凭感觉修改 prompt。

## 8. 最小数据模型

- `goals`：目标、背景、产出、时间预算和状态
- `knowledge_gaps`：目标下已知主题与待补知识
- `sources`：来源、类型、抓取配置和全局策略
- `goal_source_policies`：来源在特定目标下的权重和频率
- `items`：文章或手动内容的元数据、正文和去重指纹
- `item_goal_scores`：初筛与重排的分数、理由和模型版本
- `daily_recommendations`：每日候选、顺序及生成时上下文
- `feedback`：显式评价及原因
- `notes`：用户自己的知识笔记
- `actions`：阅读产生的行动与完成状态
- `model_runs`：模型调用记录、延迟和版本
- `policy_changes`：权重变更、原因及撤销信息

## 9. 实施阶段

### 阶段 0：建立真实测试基线

任务：

- 写下 1–3 个本人正在推进的目标
- 导出当前 RSS 订阅
- 选择 10–30 个真实信源
- 人工标注约 50 篇历史内容：必读、可读、忽略及原因
- 确认公司模型的授权范围、接口方式和数据使用边界

完成标准：

- 有一组可以反复测试推荐效果的真实样本
- 至少有一个明确目标包含当前水平、期望产出和时间预算

### 阶段 1：应用骨架与数据

任务：

- 初始化 Next.js、SQLite 和 Drizzle
- 建立核心数据表和迁移
- 完成 Goals、Sources 的基础增删改查
- 添加环境变量模板和 Docker Compose
- 建立模型适配接口及模拟实现

完成标准：

- 可以在浏览器中创建目标和 RSS 来源
- 重启应用后数据仍然存在
- 不连接真实模型也能跑通模拟流程

### 阶段 2：内容摄取

任务：

- 抓取 RSS/Atom
- 支持手动添加 URL
- 提取正文和阅读时间
- 完成 URL、标题和内容指纹去重
- 显示抓取失败及原因

完成标准：

- 真实信源可以稳定进入数据库
- 重复抓取不会产生重复内容
- 单个来源失败不会阻塞其他来源

### 阶段 3：推荐纵向闭环

任务：

- 接入公司允许使用的模型
- 实现结构化初筛输出
- 实现候选比较与最终重排
- 生成每日最多三项推荐
- 保存评分、prompt 版本和推荐理由

完成标准：

- 对基线样本生成稳定、可解释的排序
- 推荐结果能指出具体目标和价值，而不是通用套话
- 在相同输入与配置下可以复现问题

### 阶段 4：Today 与反馈

任务：

- 完成 Today 页面
- 增加阅读、保存、忽略和反馈操作
- 增加来源策略控制
- 统计来源和内容类型的有效率
- 生成权重调整建议并支持确认、拒绝和撤销

完成标准：

- 日常选择不需要查看原始 RSS 列表
- 一次反馈可以影响后续推荐或形成明确的策略建议
- 用户能解释为什么某个来源最近出现得更多或更少

### 阶段 5：阅读结果与复盘

任务：

- 增加自由笔记和结构化反思
- 从阅读中创建行动项
- 实现最小 Library
- 生成每周复盘

完成标准：

- 可以追踪一次推荐最终产生了什么知识或行动
- 周报能指出有效来源、主要噪声和下周调整建议

### 阶段 6：连续 14 天 Dogfood

任务：

- 每天真实使用，不同时查看另一个 RSS 收件箱
- 记录推荐失败案例
- 每周只修复最影响使用的前三个问题
- 比较第 1 周和第 2 周推荐有效率

完成标准：

- 按第 3 节成功标准作出继续、调整或停止判断
- 形成下一阶段需求清单，而不是凭想象增加功能

## 10. Dogfood 之后的优先顺序

只有核心闭环通过验证后，按真实痛点选择下一项：

1. YouTube 手动链接的字幕与时间戳
2. 浏览器扩展或系统分享入口
3. 书籍、章节计划和笔记导入
4. 微信读书可行的授权或数据导入方式
5. Twitter/X、播客和其他平台的自动同步
6. 更完整的知识地图和延迟复习
7. 邀请少量同事独立使用

不预先承诺顺序；连续使用数据决定下一步。

## 11. 安全与边界

- 只使用获准的公司模型、接口和凭证
- 在传输个人内容或外部全文前确认内部数据政策
- 密钥不进入 Git、数据库或普通日志
- 允许删除原文、模型记录和个人反馈
- 保留模型供应商替换能力
- 如果未来提供给公司外部用户使用，重新审查模型许可、数据政策和第三方内容条款

## 12. 立即开始的第一批任务

1. 写下第一个真实目标
2. 准备 10–30 个 RSS 信源
3. 标注 50 篇用于推荐评估的历史内容
4. 初始化应用骨架和数据库
5. 完成 Goals 与 Sources 页面
6. 跑通第一个 RSS 到数据库的摄取流程

第一条可用路径应当是：

```text
创建目标
→ 添加一个 RSS
→ 抓取文章
→ 模型排序
→ Today 展示一项推荐
→ 提交一次反馈
```

在这条路径跑通之前，不增加其他平台或复杂功能。
